## The fast way

Run this inside a project you already have. It does not create one.

```sh
npm create @luxanimi/mailgrail
```

It asks four questions — project directory, TypeScript or JavaScript, where
templates live, where compiled output goes — and then:

- adds `mailgrail`, `@faire/mjml-react`, `react` and `ejs` to your `package.json`
- adds `preview-emails` and `build-emails` scripts, plus `typecheck-emails` on a
  TypeScript project
- writes a `mailgrail.config.ts`
- scaffolds a starter template with a layout you can edit

```
emails-src/
  index.ts
  WelcomeEmail.tsx
  components/
    BaseLayout.tsx
    theme.ts
```

## By hand

```sh
npm install --save-dev @luxanimi/mailgrail
npm install @faire/mjml-react react ejs
```

`@faire/mjml-react` and `react` are peer dependencies: your template files
import them directly, and MailGrail resolves them from your project rather than
bundling its own copies.

`ejs` is different. It is imported by the **compiled output**, not by MailGrail
itself — which is what lets that output run without MailGrail installed.
Engines are declared as optional peer dependencies, so npm installs none of
them for you. Install the one matching your `templatingEngine`:

<EngineMatrix />

`mailgrail build` checks the configured engine is present and fails with an
actionable message if it is not, so a missing engine surfaces at build time
rather than when an email is sent.

That is the dependencies. The scaffolder also writes a config and four starter
files — [setting up by hand](/MailGrail/docs/getting-started/manual-setup) walks
through the rest of them, generated from the scaffolder's own source so the two
paths stay identical.

## Add the scripts

```json
{
  "scripts": {
    "preview-emails": "mailgrail preview",
    "build-emails": "mailgrail build"
  }
}
```

Both are standalone — nothing in your project calls them yet. Wiring
`build-emails` into your real build is a decision of its own, covered in
[wiring it into your build](/MailGrail/docs/getting-started/build-integration).
