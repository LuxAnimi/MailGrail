A template is a plain exported object. There is no registry, no decorator and
no base class — MailGrail finds templates because your entry point exports them.

## The shape

```ts
interface TemplateDefinition<S extends Schema<any>> {
  name: string;
  params: S;
  htmlTemplate: (mg: RenderTemplateContext<Infer<S>>) => ReactElement;
  subjectTemplate: (mg: TextTemplateContext<Infer<S>>) => string;
  textTemplate: (mg: TextTemplateContext<Infer<S>>) => string;
  sender?: string;
  category?: string;
}
```

| Field | Purpose |
|---|---|
| `name` | Output filenames and the exported function name. `confirm-email` gives `confirm-email.js` exporting `renderConfirmEmail`. |
| `params` | The schema. Types the other three fields, generates preview data, emits the `.d.ts`. |
| `htmlTemplate` | Receives the render context. Returns MJML as React elements. |
| `subjectTemplate` | Receives a render context that composes strings. Returns the subject line. |
| `textTemplate` | Receives the same context. Returns the plain-text part. |
| `sender` | Optional default `from` address, passed through to the output and typed there as the literal. Leave it out and the output has no `sender` at all. |
| `category` | Optional. Groups the template under a collapsible heading in the preview sidebar. Preview-only — it is not part of the build output. |

## One context, two kinds of output

All three template functions receive the same kind of context. `htmlTemplate`
composes React elements with it; `subjectTemplate` and `textTemplate` compose
strings.

The reason is the same in all three cases: what ships is a *template*, not a
rendered email. MailGrail has to know which parameters you touched so it can
emit placeholders the engine fills in per recipient, and the context is how it
finds out. A plain JavaScript conditional cannot do that — it runs once, at
build time, and bakes one branch into the template everybody receives.

```ts
const subjectTemplate = (mg: TextTemplateContext<Params>): string =>
  mg.when(
    "nickname",
    () => `Welcome back, ${mg.render("nickname")}!`,
    () => `Welcome, ${mg.render("username")}!`,
  );
```

Everything in the [render context](/MailGrail/docs/reference/render-context)
works here — `render`, `when`, `unless`, `each`, `with` — with the callbacks
returning strings instead of markup.

Three things differ from the HTML side:

- **Nothing is escaped.** This is plain text, where `&amp;` in a subject line
  would be a bug.
- **Newlines are yours.** They survive into the output on all three engines.
- **You cannot transform what the context hands back.** `mg.render("total")`
  returns a placeholder, not the value, so `.toFixed(2)` has nothing to work
  on. The build stops rather than ship a mangled placeholder — pass the value
  in already formatted instead.

:::caution[Mustache]
A literal `{{` in a subject or text template fails the build: Mustache has no
escape for it. EJS and Handlebars escape theirs for you.
:::

## Registering templates

The source directory needs an entry point — `index.ts`, `index.tsx`,
`index.js` or `index.jsx` — exporting a `templates` array:

MailGrail bundles that entry point with esbuild and reads the array. A template
file that nothing imports is simply never compiled, which is a convenient way
to keep a draft around without shipping it.

## Naming

`name` becomes a filename and part of an identifier, so keep it lowercase and
hyphenated. `order-confirmation` gives `order-confirmation.js` exporting
`renderOrderConfirmation`; `Order Confirmation` would not.
